# MeowFlixEmby — 方案选型与语言论证

> 第 2 部分。上一篇：[01-需求与背景分析.md](01-需求与背景分析.md)；下一篇：[03-架构设计.md](03-架构设计.md)

## 1. 触发机制选型

不用油猴脚本的前提下，"浏览器点击播放 → 本地播放器播放"有三条技术路线：

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. 投放 / 遥控目标（Cast target）** | 本地程序经 WebSocket 注册成 Emby 的可遥控会话，出现在网页端"Play On"菜单；选中后服务器把播放指令推送给本地程序 | 零浏览器改动、零服务器改动、天然跨设备、协议官方支持、可遥控（暂停/快进/停止/下一集） | 用户需点一次"投放"选目标（可记住上次目标） | ✅ **采用** |
| B. Emby 服务端插件注入 JS | 做 .NET 服务端插件，向 web 界面注入劫持 JS | 保留"点原生播放键即播" | 必须在 Emby 服务器装插件（限 .NET）；Emby 官方对 web 注入支持脆弱、需改 `index.html`；随前端改版易碎 | ❌ |
| C. 本地反向代理注入 JS | 本机跑反代，访问 Emby 时注入 JS | 无油猴、无服务端插件 | 用户须改用代理地址访问 Emby；TLS/证书复杂度高 | ❌ |

**需求方已确认选 A（投放 / 遥控目标）。**

### A 方案的用户体验说明

- 首次使用：网页端点视频 → "Play On / 播放到" → 选 `MeowFlix (本机名)`。
- 之后：Emby 网页端会记住上次投放目标，行为接近"点播放即投到本机"。
- 附带收益：网页端进度条、暂停、快进、上一集/下一集等遥控指令都能透传给本地播放器。

## 2. 语言选型：Rust / Go / .NET

需求方已确认选 **Go**。以下为完整论证。

### 2.1 本项目的技术特征

- 工作负载以 **I/O 编排**为主：维持 WebSocket 长连接、并发 HTTP 请求、子进程（播放器）管理、播放器 IPC（命名管道 / unix socket）读写。
- 几乎无 CPU / 内存密集运算（不做转码、不做解码）。
- 运行在**客户端机器**、作为**后台常驻守护进程**。
- 需要**跨平台**（Windows / macOS / Linux）。
- 需要**可作为库集成**进其他项目，也能独立运行。

### 2.2 三语言对比

| 维度 | Go | .NET | Rust |
|------|----|----|----|
| 并发模型契合度（WS+HTTP+子进程+IPC 编排） | ✅ goroutine + channel 天然契合 | ✅ async/await 良好 | ✅ tokio 良好，但心智负担高 |
| 独立运行 / 分发 | ✅ 单文件静态二进制，免运行时 | ⚠️ 需 runtime 或较大自包含产物 | ✅ 单文件静态二进制 |
| 跨平台交叉编译 | ✅ `GOOS/GOARCH` 一条命令 | ✅ 良好 | ✅ 良好（需 target toolchain） |
| 作为库被其他项目集成 | ✅ Go module；也可 `c-shared` 出 C ABI 动态库 | ⚠️ NuGet 仅限 .NET 生态；跨语言需额外封装 | ✅ crate；`cdylib` 出 C ABI 最佳 |
| Emby 服务端插件能力 | ❌ | ✅（唯一，但 A 方案不需要） | ❌ |
| 开发迭代速度 | ✅ 快、上手低 | ✅ 快 | ⚠️ 借用检查器拖慢 I/O 编排类开发 |
| 二进制体积 | 中（~5-15MB） | 大（自包含 ~60MB+） | 小 |
| 生态：Emby/媒体客户端参考实现 | 中 | 中 | 弱 |

### 2.3 结论

- 本需求是 **I/O 编排型客户端守护进程**，Rust 的性能/内存安全优势用不上，反而拖慢迭代；.NET 的独占优势（服务端插件）在 A 方案下不需要，且分发产物偏重。
- **Go** 在"单文件静态二进制、并发编排、跨平台、开发效率"上全面契合，且通过 Go module（原生）+ `-buildmode=c-shared`（跨语言 FFI）双路径满足"可插拔集成"。
- **最终选定：Go**。

### 2.4 "可插拔"如何落地（Go）

1. **Go 库集成**：核心逻辑放 `pkg/`，其他 Go 项目 `import` 即用；对外只暴露稳定的 interface 与构造函数。
2. **进程内插件**：领域能力（媒体服务器适配、播放方式决策、播放器驱动）全部基于 Go `interface`，第三方可实现接口注入自定义服务器 / 播放器。
3. **跨语言 FFI**：需要时用 `go build -buildmode=c-shared` 产出 `.dll/.so/.dylib` + 头文件，供 C/C++/Python/.NET 等 FFI 调用。
4. **独立运行**：`cmd/meowflix` 产出单文件可执行程序，带 systemd/launchd/Windows 自启脚本。

## 3. 遵循的规范与最佳实践（清单）

本项目将遵循下列公认规范，细节见 [04-Go 工程分层与规范.md](04-Go%20工程分层与规范.md)：

- **Standard Go Project Layout**（`cmd/`、`internal/`、`pkg/` 分层约定）。
- **Effective Go** 与 **Google Go Style Guide**（命名、错误处理、接口设计）。
- **Go Code Review Comments**（社区评审惯例）。
- **依赖注入 + 面向接口编程**（可插拔、可测试）。
- **`context.Context`** 贯穿所有阻塞/网络/子进程调用，支持取消与超时。
- **`log/slog`** 结构化日志（Go 1.21+）。
- **`golangci-lint`** 静态检查、**`go test` + race detector** 测试。
- **语义化版本（SemVer）** 管理对外 API 与 release。
- **Conventional Commits** 提交规范。
